# Fork patches

Every place where the fork changes code that upstream owns, and why. Changes inside fork-only files
(see [FORK.md](FORK.md#fork-only-files)) don't need an entry.

This file is what makes upstream merges safe. A merge can succeed with no conflicts and still break
a fork change: upstream renames a function a hook calls, or changes what a column means. The
`upstream-sync` skill reads each entry, checks upstream's changes against it, and uses the stated
intent to resolve conflicts. So keep entries current: add one in the same commit as the change, and
update it whenever a merge moves or rewrites the patch.

## How to add a patch

The fork is UI-only, so new patches should be rare: agree on one before adding it, and send fixes that
upstream could use as upstream pull requests instead (see
[FORK.md](FORK.md#contributing-fixes-upstream)). When a patch is needed, prefer, in order (details in
[FORK.md](FORK.md#changing-server-database-and-packages)):

1. **A plugin.** No entry needed: plugins live in fork-only directories.
2. **New files plus a small hook** in an upstream file. Mark the hook with a `FORK:` comment
   (`// FORK: <entry id>` in code, `# FORK: <entry id>` in YAML) and add an entry here.
3. **Editing upstream logic directly.** Last resort. Same marking and entry, and say in **Why**
   why a hook wasn't enough.

## Entry format

```markdown
### <entry id, kebab-case>

- **Files:** upstream files changed (fork-only files the patch adds, if any, in brackets)
- **What:** the change, in one or two sentences
- **Why:** what the fork needs it for
- **Depends on:** upstream names or behaviour the patch relies on (functions, tables, routes,
  config keys). The sync agent checks upstream's changes against these.
- **If upstream changes this:** how to resolve a conflict or breakage, and what must stay true
```

## Code patches

### runner-libc-probe-sync

- **Files:** `server/src/lib/agent-runner-platform.ts`, `server/src/__tests__/agent-runner-platform.test.ts`,
  `doc/DEVELOPING.md`
- **What:** the startup glibc probe uses `execFileSync` instead of an asynchronous `execFile`
  behind a top-level await, so slow module loading can't use up its 1 s timeout and cache
  `libc: "unknown"`. A copy of upstream PR [#17905](https://github.com/paperclipai/paperclip/pull/17905)
  (branch `fix/runner-libc-probe-startup`, commit `6f5737fd5`), plus the `FORK:` comment.
- **Why:** temporary. Without it the server offers only the Legacy runner on this machine, so
  Paperclip Runner can't be tested ([upstream-fixes 6](fork/upstream-fixes.md#6-detect-glibc-reliably-at-server-startup-so-paperclip-runner-is-offered-on-linux)).
  Added 2026-10-27 at the user's request, as an exception to keeping fix branches out of `new-ui`.
- **Depends on:** `detectLocalRunnerTarget` and `localAgentRunnerTarget` in that file, and
  `supportsLinuxLibc` in `packages/shared/src/agent-runner.ts`.
- **If upstream changes this:** if #17905 is merged, take upstream's version of all three files
  and delete this entry. If upstream fixes it another way, take upstream's version and delete the
  entry once a sync shows `supportedRunners` including `paperclip` here. If upstream rewrites the
  probe without fixing it, keep the synchronous call and the comment.
  Upstream's #21670 (2026-11-14) cut `doc/DEVELOPING.md` and moved the "Local Linux runner
  qualification" section to `doc/runner-internals.md`: take upstream's `DEVELOPING.md` and carry
  the wording change into `doc/runner-internals.md`, as the PR branch did in `3a08309e7`.


### workspace-ui-new

- **Files:** `pnpm-workspace.yaml`
- **What:** adds `- ui-new` to the workspace package list.
- **Why:** makes `ui-new` a workspace package so it can import `@paperclipai/shared`.
- **Depends on:** the `packages:` list in `pnpm-workspace.yaml`.
- **If upstream changes this:** keep upstream's version of the file and re-add the `- ui-new` line
  to the `packages:` list. Order doesn't matter.

### lockfile

- **Files:** `pnpm-lock.yaml`
- **What:** the importer entries caused by the `ui-new` package.
- **Why:** generated by pnpm from [workspace-ui-new](#workspace-ui-new).
- **Depends on:** nothing by hand.
- **If upstream changes this:** never resolve by hand. Take master's version and regenerate:
  `git checkout --theirs pnpm-lock.yaml && corepack pnpm install && git add pnpm-lock.yaml`.

## Image patches

Changes the deployment makes to upstream's built image (`deploy/Dockerfile`), not to source. They
live in fork-only files, but they change upstream's shipped server, so each one has an entry.

### deploy-runner-provider-authority

- **Files:** none in the source tree. At image build, `deploy/patches/runner-provider-authority.mjs`
  edits two compiled files in upstream's image: `server/dist/vendor/paperclip-runner/drivers/acpx/installed-provider-authority.js`
  and the `server/dist-runtime/chunk-*.mjs` bundle that inlines it (what the server runs). [Fork-only:
  `deploy/patches/runner-provider-authority.mjs`, the step at the end of `deploy/Dockerfile`.]
- **What:** `resolveInstalledProviderAuthority` returns the pnpm workspace root (`/app`) instead of
  the server package (`/app/server`) when the server sits in a workspace, so the server-side ACPX
  verifier accepts the Claude and Codex bridges. A build-time copy of upstream PR
  [#20710](https://github.com/paperclipai/paperclip/pull/20710) (issue #18557), with the same rule
  as `sourceWorkspaceProviderRoot` there.
- **Why:** temporary. Without it, Claude and Codex agents on the Paperclip Runner fail their
  environment test in the Docker image and never run
  ([upstream-fixes 28](fork/upstream-fixes.md#28-let-claude-runner-agents-pass-verification-in-the-docker-image)).
  Added 2026-11-15 at the user's request. Local `pnpm dev` doesn't need it: the failing check only
  applies to the vendored build.
- **Depends on:** a `function resolveInstalledProviderAuthority(` that ends with
  `return { root, manifest };`, in the vendored file and in exactly one `server/dist-runtime/*.mjs`
  file; the image layout (`/app/server` in a workspace with `node_modules/.pnpm`,
  `pnpm-workspace.yaml`, root package `paperclip`); Node with `process.getBuiltinModule` (22.3+).
- **If upstream changes this:** the script skips a copy that already calls
  `sourceWorkspaceProviderRoot`, and fails the image build if the function no longer ends as
  expected. If #20710 (or another fix for #18557) is in the base image: the build log says
  "already has upstream's fix" for both copies; delete the script, the Dockerfile step and this
  entry, and move Claude agents back to the Paperclip Runner. If the build fails on a rewrite
  without the fix, update the script to the new code and keep the same rule. To check a new base
  image during a sync, before deploying (patches only the throwaway container and prints what it did):
  `docker run --rm --network none --entrypoint node -v "$PWD/deploy/patches:/p:ro" ghcr.io/paperclipai/paperclip:sha-<sha> /p/runner-provider-authority.mjs`
