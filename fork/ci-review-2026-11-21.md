# CI review, 2026-11-21

A look at the test suite and CI after step 3a, and at every CI run on GitHub so far. Written with
the `ci-cd-and-automation` and `github-actions-efficiency` skills. The follow-up guide for pushes
that come back green is [green-push.md](green-push.md).

## Summary

- **The setup suits the fork.** One workflow instead of upstream's 38, two tiers that leave the
  dormant code out of the push run, pinned actions, read-only permissions, newer pushes cancel older
  runs, and deploys gated on a green run. Most solo projects have less.
- **The failures fall into two groups.** Since the fork's workflow started (2026-11-19), 12 of 30
  runs had a red attempt: 9 from flaky tests and 3 from mistakes a local check could have caught.
  Every flake but one (bug 68) is fixed. The 3 caught-late failures share one cause: `test:quick`
  doesn't select the cross-cutting contract tests.
- **Three changes would help most.** First, make `test:quick` always run the contract tests.
  Second, run the whole workspace typecheck before pushing. Third, record every re-run, because a
  re-run that passes hides the flake from the run history.
- **Wall time is fine.** About 10.7 minutes, set by the typecheck job, not the shards. Two small
  changes would bring it to about 8.5.

## What's there

| Piece | What it does |
| --- | --- |
| `scripts/test.mjs` | Tiers, sharding by expected time, a default worker count from the machine, and a coverage check that every file runs exactly once. It has its own tests (`test:runner`). |
| `scripts/test-tiers.json` | ~180 `optIn` globs, each with a reason, that keep dormant code out of the thorough tier. |
| Thorough tier | 1,451 files, run in CI on every push: 10 shards of ~145 files, ~21 expected worker-minutes each. |
| Opt-in tier | 1,335 files (dormant halves, Runner, other adapters, CLI, plugins, chat channels). Nothing runs it automatically. |
| Quick tier | The tests a change touches since its merge base with `main`, chosen by name, relative import and small directories. |
| `.github/workflows/test.yml` | Typecheck job (workspace typecheck, ui-new tests, runner tests) and the 10-shard thorough matrix. Caches the pnpm store and Vitest's module cache, uploads JSON reports. |
| `deploy/deploy.sh` | Deploys only a commit whose CI run passed. In practice this is the fork's branch protection. |

## CI runs

83 runs from 2026-10-15 to 2026-11-21. The 53 on `master` were upstream's old workflows and don't
count. The fork's own workflow has run 30 times since 2026-11-19:

- 18 green on the first attempt
- 4 green only after a re-run
- 8 red
- 2 cancelled by a newer push

A green run takes 11.5 minutes at the median.

### Flaky tests: 9 runs

| Test | Red runs | Cause | Status |
| --- | --- | --- | --- |
| `run-start-handover` ("the old server stops starting runs…") | 4 | Background heartbeat runs outliving their file | fixed, bug 62 (`d5435c29b`) |
| `heartbeat-worktree-suppression` (afterEach hook timed out) | 3 | Same leak, in shard 5 | fixed, bugs 62 and 64 |
| `heartbeat-task-drain` ("expected 1 to be +0") | 1 | A run left behind by another file | fixed, bug 64 (`877fe4dd7`) |
| `issue-recovery-activity-hints` ("expected 8 to be ≤ 6") | 1 | Idle worker deadlines on 2 CPUs | fixed (`467b35d79`, bug 66) |
| `fresh-continuation-fallback` ("recycled PID") | 1 | Timing around the process start-time probe | **open, bug 68** |

All the fixed ones were timing tests sharing one worker with another file's leftovers, and the
fixes went at the cause (drain in `afterEach`, isolate the file). That's the right approach.

Four of these runs show as green in the run list, because the failed job was re-run and passed. A
re-run overwrites the run's result, so a flake you re-run leaves no trace in `gh run list`. Bug 68
is on the list only because someone wrote it down.

### Caught late: 3 runs

| Run | What broke | What change caused it | Local check that would have caught it |
| --- | --- | --- | --- |
| `feat/step-4b-p2-preview`, `ui/agent-run-preview` (2026-11-21) | `openapi-routes`: `GET /api/agents/{id}/run-preview` missing from the spec | `1046fb8f6` added the route in `server/src/routes/agents.ts` without an entry in `server/src/routes/openapi.ts` | Running `openapi-routes.test.ts` |
| `feat/step-4b` (2026-11-20) | `issue-detail-statements`: golden file lacks `agentsReadClaudeMd`, `agentsUseRepoSkills` | `20b51b74e` added two project fields | Running `issue-detail-statements.test.ts` |

I ran `selectChangedTests` on both commits: `test:quick` selected 56 and 92 files, but neither
contract test. That's by design, since quick chooses by name and import, and these two tests check
the whole app (every route, the full issue response). So a developer who followed the documented
pre-push step (`test:quick`) still pushed a red run. The two tests take 36 s together locally.

The typecheck failure is the same pattern in another form. A shared type changed, and a dormant
package's fixture builds that type. The typecheck only reaches it when it runs over the whole
workspace, which takes ~3 minutes on the desktop.

## Is it right for the hard fork?

Mostly yes.

- **Tier split.** The `optIn` globs follow the hard-fork plan's dormant list closely, and each one
  has a reason. The thorough tier fell from 2,736 files to 1,451, so the push run tests what you
  run. I didn't audit the 1,451 test by test. Classifying by area (step 3a) was the right level for
  that.
- **Dormant packages are still typechecked.** The workspace typecheck covers the other adapters,
  plugins, the CLI and the Runner's `cargo check` (~85 s, which runs alongside the server typecheck
  and so isn't on the critical path). That caused one failure, but it's cheap and it's how a change
  to a shared type shows up everywhere it's used. **Keep it.** The test files of those packages are
  opt-in, but their types still have to compile.
- **The opt-in tier rots.** Bug 69 (opt-in hiring and portability tests behind step 4a's access
  levels) shows it: nothing runs those 1,335 files, so they drift from the core a little with every
  change. That's acceptable for dormant code, until you want to wake some of it up or upstream a
  fix. A weekly scheduled run that only reports, and doesn't block, would show the drift while it's
  still small.
- **Tests worth questioning.** The flaky tests are upstream's multi-server and timing tests
  (deploy-overlap hand-over, heartbeat drain, recovery budgets). They test code this fork does run,
  so they stay. `run-start-handover` checks two servers overlapping during a deploy. If server1's
  Compose swap never runs two servers at once, that test guards a case you don't have. Worth a
  look, not a removal yet.
- **Statement-count and golden tests** (`issue-detail-statements`, `issue-recovery-activity-hints`'
  "≤ 6") are good tests: they catch performance regressions and unintended response changes. They
  also break on every intended change, which is why they should be in the pre-push set.

## Against a strong CI pipeline

Using the `ci-cd-and-automation` skill's quality gates and checklist:

| Gate or practice | Strong pipeline | Here | Verdict |
| --- | --- | --- | --- |
| Lint / format | ESLint, Prettier on every change | None (no ESLint config in the repo) | Low priority. Typecheck catches most of what matters, and adding a linter to an upstream-sized codebase is a project of its own. |
| Typecheck | Yes | Yes, whole workspace | ✓ |
| Unit and integration tests | Yes, sharded when large | Yes, 10 shards, real Postgres per test | ✓ |
| Build | `build` on every change | **No.** ui-new's `vite build` and the Docker image are built first by `deploy.sh` | Gap. A broken build shows up at deploy time on server1. |
| E2E | Playwright on PRs, report on failure | **No.** ui-new's mocked Playwright suite (`test:e2e`) exists but CI doesn't run it | Gap. It's cheap and needs no server. |
| Security audit | `npm audit`, Dependabot | None | Optional for a solo fork that freezes upstream's lockfile. |
| Runs on every push | Yes | Yes, every branch | ✓ |
| Failures block merge | Branch protection with required checks | No protection. `deploy.sh` refuses commits without a green run | Fine for one person pushing straight to `main`. The deploy gate is where it counts. |
| Flakes | Fixed, not re-run | Fixed at the cause, but re-runs go unrecorded | Mostly ✓ (see recommendation 3) |
| Rollback | Yes | `deploy.sh --rollback` (no-migration deploys), backups before migrations | ✓ |
| Secrets | Not in CI | None used, `contents: read` | ✓ |
| Under 10 minutes | Target | ~10.7 min wall, ~95 runner-minutes per push | Close |
| Slow tiers on a schedule | Yes | Opt-in tier never runs | Gap (bug 69) |

## Efficiency (github-actions-efficiency audit)

Measured on run 44960577747 (2026-11-21, green):

- **The critical path is the typecheck job, not the shards:** typecheck 312 s, then ui-new tests
  244 s, then runner tests 37 s, all in series, 10.7 minutes in total. The slowest shard took 9.9
  minutes.
- **The shards are unbalanced:** 359 s to 542 s of test time. The weights come from
  `classification.csv`, where 304 files have local timings, the rest have upstream's CI timings or
  the median, and none of it has been refreshed from this workflow's uploaded reports.
- **The caches work.** Install takes ~21 s from the pnpm store cache.
- **Concurrency cancellation works.** Two runs were cancelled by a newer push.
- **Docs-only pushes run the whole suite.** 23 of the 75 commits since 2026-11-19 change only
  Markdown, and each push costs ~95 runner-minutes. The repo is public, so the minutes are free,
  but every extra run is another chance for a flake.

Fixes that pass the skill's guardrails, ranked by benefit:

1. **Move ui-new's tests into their own job.** The typecheck job drops to ~6.5 minutes, so the
   shards become the critical path (~9.9 min). This doesn't drop any check, and the jobs still run
   in parallel.
2. **Refresh the shard weights from CI's JSON reports.** The reports are already uploaded for this,
   and balancing at the mean (~463 s) puts the slowest shard near 8.5 minutes. Together with fix 1,
   that's **10.7 → ~8.5 minutes wall**. Expected, not measured.
3. **Skip the shards on docs-only pushes, at the job level.** Use a small job that checks the
   changed paths, and gate the matrix on it. Don't use workflow-level `paths-ignore`: a skipped
   workflow leaves the commit with no run, and `deploy.sh` would refuse to deploy it. With a job
   that's skipped inside a green run, `deploy.sh` already accepts it, since it ignores skipped jobs.
   This saves ~95 runner-minutes per docs push. I'd rank it last, because it adds a moving part to
   save minutes that cost nothing.

None of these were checked live on GitHub. They're expected figures from one run's timings.

## Recommendations

In order. 1–3 prevent most red pushes, 4–6 close gaps, 7–8 make it faster.

1. **Contract tests in `test:quick`. Done 2026-11-21** on `test/quick-contract-tests`.
   `scripts/test-tiers.json` has an `alwaysQuick` list (`openapi-routes`,
   `issue-detail-statements`, `authz-existence-oracle-guard`), and quick adds it to any change that
   isn't only Markdown. Replayed on the two commits behind the caught-late runs, quick now selects
   both failing tests. It adds ~40 s.
2. **Whole-workspace typecheck before every push** (`corepack pnpm typecheck`), not only the
   package you changed. That would have caught the third. **Done 2026-11-22:** a pre-push hook
   (`.githooks/pre-push`, `scripts/pre-push.mjs`, `corepack pnpm hooks:install`) runs it and
   `test:quick` on the pushed range, unless only Markdown changed.
3. **Record every re-run.** A red job you re-run gets a line in the bug list (or a "flakes" table
   in it) before you press re-run. That keeps the run history honest. Fix bug 68. **Done
   2026-11-22:** the rule is in [green-push.md](green-push.md), and `scripts/ci-flakes.mjs` lists
   every re-run and red run with the tests that failed. Bug 68 failed twice more the same day, then
   was fixed (a test-only bug: a recorded start on a whole second, 1 run in 100; `875621d3f8`), with
   the same flaw in a second test. Bug 79, a new step 4b test racing another file's temp folders,
   was found and fixed the same way (`00e44a3661`). The pre-push hook is on in this
   clone (2026-11-22) and holds the machine lock while it checks.
4. **Add ui-new's build and its mocked Playwright suite to CI**, as a job of their own. Both are
   fast and need no server, and they move build breaks from deploy time to push time. **Done
   2026-11-22:** a `ui-new` job (unit tests, `vite build`, mocked e2e; ~6 min). Beyond the review:
   each shard's failed tests now show on the run's page (`scripts/ci/summarize-reports.mjs`), and a
   gated job builds both Docker images when a push changes what they're built from (~11 min,
   measured on run 44977462841).
5. **A weekly opt-in run** (`schedule:` plus `workflow_dispatch`, sharded, reports only), so dormant
   code drifts visibly (bug 69). **Done 2026-11-22:** `.github/workflows/optin-weekly.yml`, Mondays,
   10 shards. Its first run comes after `main` is pushed. Also: `.github/dependabot.yml` now asks for
   security updates only (upstream's asked for up to 40 version-update pull requests a week), and
   Dependabot alerts are on in the repository's settings (2026-11-22); automatic security-fix pull
   requests stay off until the alert list shows how many there are.
6. **Decide whether `run-start-handover` guards a case you have** (two servers overlapping during a
   deploy). If not, it can go to opt-in. **Decided 2026-11-22: keep it.** `deploy.sh` restarts the
   one server container (`docker compose up -d --force-recreate server`), so deploys never overlap
   two servers. But the hand-over code still runs at every start, the test has been steady since
   bug 62's fix (2026-11-20), and moving it to opt-in would save nothing.
7. **Split the typecheck job and rebalance the shards** (efficiency fixes 1 and 2). **Done
   2026-11-22, effect not yet shown:** with ui-new on its own job the typecheck job went from
   10.7 to ~4.7–7 min. The shards are weighted by CI's own timings (`scripts/test-weights.json`,
   `scripts/refresh-shard-weights.mjs`). Its first run measured 351–559 s per shard, within
   run-to-run noise of before; judge it over several runs on `main`. One known limit: a 73 s
   file alone in one shard's packages phase, because shards are balanced phase by phase.
8. **Job-level docs-only skip** (efficiency fix 3), if flakes on docs pushes keep costing re-runs.
   Not done.
